# CSight 제품 방향 전환 기록

- 기록일: 2026-08-28
- 대상 브랜치: `codex/operator-console-product-direction`
- 목적: 지금까지의 구현이 왜 모델 중심 기술 검증에서 실제 상담 업무를 닮은 운영형 제품으로
  이동했는지, 그 과정에서 무엇을 채택하고 무엇을 보류했는지 설명한다.

## 1. 처음에 검증하려던 것

초기 CSight의 핵심 질문은 이미지와 문의 내용을 분석하고, 관련 정책을 검색해 근거가 있는 권고를
만든 뒤, 사람이 최종 결정을 내리는 전체 기술 경로를 구축할 수 있는가였다. 이에 따라 먼저 다음
기반을 만들었다.

- Tenant 격리, Case와 Private Evidence 저장
- Text/Vision 비동기 분석과 append-only 실행 이력
- 정책 문서 적재, Hybrid Retrieval, 인용 근거와 Grounding
- 버전 관리된 정책 규칙과 평가
- 인증된 담당자만 확정할 수 있는 Human Review
- Human Decision 이후의 Resolution, Action Intent와 외부 처리 전 검증

이 단계는 시스템의 안전성·복구성·추적 가능성을 검증하는 데 필요했지만, 실제 상담원이 사용하는
제품의 모습과는 거리가 있었다. 화면에는 내부 상태값과 모델 qualification 정보가 많이 노출됐고,
주문·고객·환불 문맥이 부족해 기술 구성 요소를 연결해 놓은 개발 콘솔처럼 읽혔다.

## 2. 방향을 바꾸게 된 직접적인 근거

### 2.1 실제 Vision 연결만으로는 업무 시나리오가 완성되지 않았다

비전 담당자가 전달한 E3는 실제 checkpoint로 연결했지만, 현재 계약은 이미지 단위의
`any-defect` 이진 점수다. 상품명, 결함 유형, 결함 위치, 환불·교환 같은 업무 결정을 예측하는
모델이 아니다. 높은 점수를 특정 결함이나 처리 유형으로 해석하거나 낮은 점수를 정상으로 확정하면
모델이 제공하지 않은 의미를 시스템이 만들어 내게 된다.

Kaputt 원본 라벨에도 상품명이 없었다. Qwen VLM으로 상품 메타데이터와 결함 설명을 보강하는
실험을 했지만, 상품 taxonomy 정합성과 defect-positive 재현이 충분하지 않았다. 따라서 Qwen의
결과를 공식 라벨이나 최종 업무 판단으로 승격하지 않고, 후보 메타데이터를 만드는 오프라인 연구
경로로 분리했다.

### 2.2 실제 기업 데이터 없이도 전체 제품 동작을 보여줄 필요가 있었다

현재 단계에서는 실제 기업 정책, 고객 개인정보, 결제·배송 시스템을 사용하지 않기로 했다.
그러나 단순한 짧은 문의와 모델 점수만으로는 “실제 서비스에서 어떻게 쓰이는지”를 보여주기
어려웠다. 그래서 검증된 이미지에 가상의 상품명·SKU·가격대·문의 내용과 고객·주문·결제·배송
문맥을 붙여 상담원이 처리하는 한 건의 업무처럼 읽히도록 구성했다.

이 데이터는 현실감을 위한 표시·문서 문맥이며 Action parameter의 출처가 아니다. 환불 금액과
통화, 교환 수량, 배송지 참조는 사용자가 명시적으로 입력한 값만 사용한다. 주문 금액이나 고객
문의, 모델 설명에서 값을 추론하지 않는다.

### 2.3 기술이 아니라 상담 업무 흐름을 보여줘야 했다

초기 콘솔의 `APPROVE_REFUND`, `REQUIRES_HUMAN_REVIEW`, qualification JSON, Mock/DRY-RUN
표시는 개발자에게는 유용하지만 상담원이 빠르게 읽기 어렵다. 실제 사용 관점에서는 현재 할 일,
진행 단계, 상품명, 문의 내용, 사진, 정책 근거, 허용·비허용 선택과 처리 결과가 먼저 보여야 했다.

이에 따라 화면을 다음 흐름으로 다시 설계했다.

1. 상품명 중심으로 문의와 검토 작업을 찾는다.
2. 문의 내용과 이미지 근거, 정책 권고를 한 화면에서 확인한다.
3. 담당자가 허용 또는 비허용을 직접 선택한다.
4. 결정과 근거를 변경 불가능한 기록으로 남긴다.
5. 환불 처리 확인서와 고객 안내 메일을 업무 문서 형태로 확인한다.

기술 상태값은 API와 감사 기록에 보존하되, 첫 화면에서는 자연어 업무 표현을 사용한다.

## 3. 최종적으로 채택한 제품 원칙

### 사람의 결정이 최종 결정이다

LLM, Vision, Retrieval과 정책 규칙은 근거와 권고를 제공한다. 환불·교환·재배송·수리 여부는
로그인한 담당자의 명시적 행동으로만 확정된다. 빠른 검토 버튼도 모델이 자동 처리하는 기능이
아니라, 준비된 정책 근거를 붙여 담당자의 결정을 기록하는 단축 경로다.

### 운영 문서는 현실적으로, 외부 실행 여부는 정직하게 표시한다

환불 확인서에는 고객, 주문, 결제, 배송, 승인 근거, 환불 예정 금액과 처리 이력을 표시한다.
고객 안내 메일도 실제 발송될 형태로 생성한다. 다만 현재 외부 결제사, CRM, SMTP에는 연결하지
않으며 화면에 `외부 시스템 미반영`, `실제 발송 없음`을 명시한다. 기술 용어를 숨기는 것과 실제
실행이 일어난 것처럼 보이게 만드는 것은 구분한다.

### 모델이 제공한 범위 이상을 주장하지 않는다

현재 E3는 이진 결함 후보 점수만 제공한다. 제품군과 결함군은 사람 승인 Allowlist와 원천 라벨로
구성하고, E3 점수는 선별 기준으로만 사용한다. 20건 구성은 네 상품군과 세 결함군을 화면에서
표현하지만 정확도, calibration 또는 시장 분포 성능을 의미하지 않는다.

### 데이터는 나중의 개선에 쓰일 수 있게 구조화하되 개인정보 원문은 쌓지 않는다

최종 검토 보고서에서 상품군, 결정, 결과, 모델·정책 버전과 처리 상태를 tenant별 append-only
학습 자산으로 남긴다. 고객 문의 원문, 이름, 전화번호와 주소 같은 직접 개인정보는 학습 자산에서
제외한다. 이 구조는 이후 데이터 드리프트와 정책·모델 변화 비교에 사용할 수 있지만, 아직 실제
고객 성능을 측정한 데이터는 아니다.

### 내부 계약과 사용자 언어를 분리한다

DB enum, Event name, API schema와 hash snapshot은 호환성과 감사 가능성을 위해 유지한다.
상담원 화면과 출력 문서에서는 `처리 사전 확인`, `담당자 확인 후 결정 필요`, `안내 메일 만들기`
같은 업무 표현을 사용한다. 기존 불변 기록에 개발용 표식이 남아 있어도 저장 원본을 변경하지 않고
표시 단계에서 정리한다.

## 4. 이번 방향 전환에서 실제로 추가된 것

- 20건의 사람 승인 이미지 closed set과 네 상품군·세 결함군 시나리오
- 현실적인 한글 상품명, SKU, 가격대와 긴 이커머스 문의 내용
- 검증된 고객·주문·결제·배송 문맥과 마스킹된 표시 정보
- 상품명 중심 문의 목록과 검토 대기함
- 문의·이미지·정책 근거를 연결한 상담원 작업 화면
- 담당자 허용·비허용 빠른 검토와 변경 불가능한 Human Decision
- 실제 운영 양식을 참고한 환불 처리 확인서와 인쇄 화면
- 외부 전송 없는 고객 안내 메일 생성·열람
- tenant별 비식별 append-only 데이터 자산 원장
- 상담 운영 지표와 자연어 상태·정책·qualification 표현

## 5. 의도적으로 구현하지 않은 것

다음 항목은 화면에서 비슷한 흐름을 보여주더라도 실제 기능으로 구현하거나 실행하지 않았다.

- 카드 승인 취소, 계좌 환급과 실제 환불
- 교환·재배송·수리 주문 생성
- CRM, 결제사, 물류사, SMTP 연동
- 실제 고객 연락과 이메일 발송
- 모델이나 정책의 자동 최종 승인
- 고객 문의에서 금액·통화·수량·배송지를 추론하는 기능
- Human Decision 수정과 자동 Case Closure
- 실제 기업 데이터에 대한 성능·ROI 주장

이 경계는 기능 부족을 감추기 위한 것이 아니라, 실제 데이터·권한·외부 시스템이 준비되지 않은
상태에서 잘못된 실행과 과장된 성능 주장을 막기 위한 제품 결정이다.

## 6. 현재 상태의 정확한 해석

현재 CSight는 전체 상담 업무가 어떻게 연결되는지 보여줄 수 있는 내부 운영형 제품이다. 실제 E3
checkpoint, 정책 검색·평가, Human Review, Resolution, 보고서와 데이터 자산 경로가 연결돼 있다.
하지만 데이터와 정책은 현재 범위에 맞춰 구성한 것이며, 실제 기업 사용 성능을 입증한 상태는
아니다.

따라서 현재 결과로 주장할 수 있는 것은 다음과 같다.

- 이미지와 문의를 분석하고 정책 근거를 담당자에게 전달하는 기술 경로가 동작한다.
- 담당자 결정 이후 처리 요청을 안전하게 검증하고 감사 가능한 문서를 만들 수 있다.
- 실제 상담 업무에 가까운 UI와 데이터 구조로 전체 흐름을 설명할 수 있다.
- 모델·정책·결정·결과 metadata를 추후 품질 비교가 가능한 형태로 축적할 수 있다.

현재 결과만으로 주장할 수 없는 것은 실제 고객사의 결함 탐지 성능, 상담 시간 절감률, 자동화율,
환불 정확도와 ROI다.

## 7. 다음 단계

내부 제품 시연 이후 실제 고객 환경으로 이동하려면 다음 순서가 필요하다.

1. 대상 상품군과 결함 taxonomy를 고객 업무에 맞게 확정한다.
2. 비식별 실제 사례와 상담원·전문가 Gold를 확보한다.
3. 실제 정책 문서와 효력일을 적용하고 검색·규칙 결과를 평가한다.
4. 제품군별 Vision 성능과 threshold를 독립 평가한다.
5. 실제 실행 없이 Shadow Mode로 사람 결정과 비교한다.
6. 개인정보 보관·삭제, 접근권한과 외부 시스템 연동 승인을 받는다.
7. 모든 안전 Gate를 통과한 뒤에만 제한된 실제 연동을 별도 기능으로 설계한다.

이번 방향 전환의 핵심은 “AI가 환불을 결정하는 화면”을 만드는 것이 아니라, AI와 정책이 근거를
준비하고 사람이 안전하게 결정하며 그 결과를 실제 업무 문서와 데이터 자산으로 연결하는 제품을
만드는 것이다.
