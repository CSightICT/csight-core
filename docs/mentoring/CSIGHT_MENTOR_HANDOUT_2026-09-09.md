# CSight 기술 멘토링 공유자료

## 개선 반영 후 시스템 현황과 핵심 질문

기준일: 2026-09-09 · 대상: 기술 멘토

최근 개선 작업까지 반영한 회의용 요약이다. 구현된 기능, 실제로 확인한 범위, 앞으로 검증할
가설을 구분했다. 멘토링 답변·승인이나 출시 일정을 미리 확정한 문서가 아니다.

## 1. 먼저 말씀드릴 내용

CSight는 **고객 문의와 상품 사진을 분석하고 기업 정책의 근거를 찾아, 상담원의 불량·교환·
환불 관련 검토를 돕는 B2B CS 의사결정 지원 서비스**다. 일반 FAQ 챗봇이나 자동 환불 서비스와는 다르다.

핵심 AI는 Vision과 LLM이다. LLM은 문의 구조화·검색 질의 생성·정책 근거 설명의 세 역할을
맡고, Vision은 이미지에서 관찰한 결함 후보 정보를 제공한다. 그 위에 정책 검색(RAG),
버전 관리된 규칙, 상담원 검토, 접근 통제와 감사 기록이 결합된다.

기본 업무 흐름은 다음과 같다. 각 모델의 출력은 업무 결정이 아닌 분석 근거다.

```text
문의·사진 접수 → 텍스트/이미지 분석 → 관련 정책 검색·근거 설명
              → 정형 정책 조건 검토 → 인증된 상담원의 최종 결정 → 보고서·모의 처리
```

최근 만든 ‘고객 주장↔이미지 대조’ 기능은 이 업무 흐름에 아직 연결하지 않은 오프라인
진단 모듈이다. 실제 환불·메일·CRM 쓰기 또한 연결하지 않고 모의 처리(DRY_RUN)로 제한한다.

**현재는 내부 시연 기반까지 구현됐지만, 실제 고객 파일럿과 최종 모델 승격은 차단된 상태다.**
RAG나 사람 검토를 처음부터 만들어야 하는 단계는 아니다. 지금 가장 필요한 것은 실제 고객
자료에서 품질을 검증하고, 첫 고객 환경에서 안전하게 운영할 조건을 확정하는 일이다.

우리는 최저 응답 시간보다 **의미·근거의 품질 → 불확실성과 안전 → 업무 처리 가능성 → 속도**를
우선한다. 문서당 약 5분에 이르는 대기는 피하고자 하지만 정식 지연 목표는 아직 확정하지 않았다.
어떤 과제의 필수 품질·안전 실패도 다른 과제의 높은 점수로 상쇄하지 않는다.

## 2. 현재 시스템 현황

‘구현’은 코드·계약이 있다는 뜻이며 고객 환경의 운영 자격이나 모델 정확도 보증이 아니다.

| 영역 | 현재 갖춘 것 | 아직 확인하거나 결정할 것 |
|---|---|---|
| 서비스 기반 | Python/FastAPI 모듈형 모놀리스, 외부 기술을 ports/adapters로 분리 | 첫 고객의 배포 형태·운영 책임·변경 절차 |
| 저장·비동기 처리 | PostgreSQL/pgvector, private MinIO, RabbitMQ/Celery, Outbox·멱등성·재시도·불변 분석 이력 | 실제 부하·부분 장애·복구·재실행/취소의 고객 운영 자격 |
| 상담원 화면 | React/TypeScript 콘솔, 접수·배정·검토·추가 자료 요청·사람 결정·보고서 | 상담원 사용성·수정량·재문의율, 실제 CRM 연동 |
| LLM | 문의 구조화, Query Builder, 근거 설명과 과제별 실행 버전 계약 | 최종 동일 모델·프롬프트·런타임 구성의 세 과제 공동 품질 검증 |
| Vision | E3의 이미지 전체 ANY_DEFECT 점수를 연결 | 결함 종류·위치·bbox는 E3 출력에 없음. 낮은 점수도 정상 확정이 아님 |
| VLM | GX10에서 합성 이미지의 기본 응답 기록 | 실제 고객 사진의 미세 결함·OCR·여러 사진 비교는 미자격. 전용 Vision 대체 여부 미정 |
| RAG | 정책 조항·버전, BM25+dense+RRF 검색, 고객사·유효기간 선필터, 고정된 인용 근거 묶음 | 실제 정책의 표·각주·예외 연결과 갱신 절차, 고객 분포의 검색 품질 |
| 정책·사람 결정 | 검색/생성 설명과 분리된 정형 정책 엔진, 인증된 사람만 최종 결정 | 고객 정책 검수·효력 시점·불완전 조건 처리와 실제 전체 경로 검증 |
| 주장↔이미지 대조 | 유형 후보·미확인 이유·추가 자료 요청을 만드는 오프라인 진단 | 실제 결합 효과, 운영 저장/API/UI·권한·보존·정책 연결 |
| 보안·개인정보 | OIDC/PKCE·역할/소유권·DB RLS·파일 정화/검사, 원문/파생본 삭제와 기록 분리 | 고객 IdP·권한 회수·자료 사용권·보존/백업·키 운영 계약 |
| 배포·운영 | 데모와 분리된 제한 파일럿 구성·진입 점검, 관측·복원 절차 | 실제 고객 환경의 부하·경보 수신·별도 호스트 반복 복원 증거 |

모델 환경도 구분한다. RTX 4090의 Q5 후보와 GX10의 사용자 설치
`RadixArk/Qwen3.8-27B-NVFP4`는 서로 다른 평가 대상이다. 이름이 비슷하다는 이유로
정확도·안전성·출시 자격을 서로 넘겨쓰지 않는다.

## 3. 이번에 먼저 개선한 부분

| 완료한 개선 | 해결한 문제 | 이 개선만으로 증명되지 않는 것 |
|---|---|---|
| 검색 평가 지표 분리 | ‘하나라도 찾음’과 ‘필요한 조항 중 얼마나 찾음’을 구분. 본문을 찾고 예외를 놓친 실패가 드러나게 함. 빈 Gold·중복 히트도 차단 | 실제 검색기나 모델의 정확도 향상 |
| 평가 실행·결과 보호 | 기존 두 평가 도구를 Dev 전용으로 제한. Test 오사용·자동 freeze·과거 결과 덮어쓰기 차단. 원문 미출력, 미측정 항목은 null/NOT_RUN | 정식 최종 평가 또는 출시 승인 |
| 이미지 숨은 정보 제거 | 정화 후에도 남던 합성 PNG의 ICC·JPEG 주석 등 원본 metadata 제거, 회전·투명도 회귀 보강 | 실제 고객 정보 유출 발견, 색관리 동등성 또는 전체 개인정보 적합성 |
| 악성 파일 검사 보강 | ClamAV의 분할·비정상 응답, 크기/시간 상한 처리와 오류 시 업로드 차단 | 실제 고객 배포 환경의 보안 자격 재검증 |

예를 들어 정답 정책이 ‘본문+예외’ 두 조항인데 본문만 찾으면, 하나 이상 찾은 비율(HitRate)은
1.0이지만 조항 회수율(Clause Recall)은 0.5, 전체 정답 포함 여부(Exact Gold coverage)는 0.0이다.
이 수치는 계산 설명을 위한 예시이지 현재 모델 성적이 아니다.

과거 후보 평가의 `recall_at_10`은 이름과 달리 HitRate 의미였으므로 기존 기록과 기준을 보존했다.
새 조항 Recall은 별도 버전의 진단 지표이며, 과거 합격 기준을 그대로 가져와 사용할 수 없다.

코드 lint/타입 검사는 통과했다. 저장소 전체 서식 검사에는 이번 수정과 무관한 기존 사용자
문서 1개의 경고가 남아 있으며 보존했다. 이번 공유자료 작성에서는 위 테스트나 서버 검사를
다시 실행하지 않고, 개선 완료 시점의 검증 기록을 대조했다.

모델 후보 상태는 `NO_WINNER` / `NO_RELEASE_ELIGIBLE`이다. 사람 승인 기능이 없어서가 아니라,
최종 모델의 공동 품질·안전 자격과 실제 고객 운영 조건이 아직 충족되지 않았기 때문이다.

## 5. 멘토님께 여쭙고 싶은 핵심 질문 12개

각 질문은 ‘현재 상황 → 질문 → 회의에서 얻고 싶은 결과’ 순서다. 모델 교체·학습·설비 구매를
선행 결론으로 두지 않고, 비교할 선택지와 검증 기준을 받고 싶다. 괄호의 ID는 전체 질문 목록과 연결된다.

### Q01. 첫 출시의 지원 범위를 어디까지 좁히는 것이 적절할까요?

현재 고객 1곳·상품군 1개·시각적 결함 2~3개로 시작하는 안이 있으나 대상은 미확정이다.
시각적으로 확인 가능한 불량, 문의 빈도, 정상 참고 사진 확보 가능성, 오류 비용 중 무엇을
우선해 골라야 할까? 사진으로 판단할 수 없는 작동·냄새·책임 문제는 어떤 수동 경로로 제외할까?

받고 싶은 결과: 첫 지원/제외 범위와 상담원에게 제공할 최소 기능 1장. (A01, A02, A05)

### Q02. 두 엔진을 제대로 평가하려면 어떤 데이터와 독립 정답부터 모아야 할까요?

합성 평가와 선별 시연 자료는 있지만 실제 문의·전체 사진·주문 맥락·당시 정책이 연결된
대표 자료가 부족하다. 고객 주장, 사진에서 관찰 가능한 사실, 정책상 처리의 정답을 어떻게
분리하고 검수할까? 동일 상품·주문·촬영·유사 이미지 누출을 막는 분할과 표본 구성은 어떻게 정할까?

받고 싶은 결과: 최소 Case Bundle, 라벨/이견 조정 기준, 검수자, 그룹 분할·사용권 확인표.
초기 소량 수집과 통계적 품질 보증에 필요한 표본은 분리한다. (B01–B04, M02)

### Q03. 무엇을 측정하고 어느 수준이어야 제한 파일럿을 허용할까요?

코드 회귀와 실제 모델 품질은 별개이며 새 조항 Recall에도 아직 정식 합격 기준이 없다.
잘못된 정책 적용·근거 없는 확신·개인정보 노출처럼 중대 위험은 어떤 절대 기준으로 막고,
추출·검색·설명·Vision·대조·업무 효과는 어떤 분리 지표와 신뢰구간으로 평가할까?
AI 채점 보조와 사람 검수를 어떻게 구분하고 Dev 반복·설정 고정·최종 Test 접근을 통제할까?

받고 싶은 결과: 위험별 평가 카드, 사람 검수 범위, 표본 계획과 새 지표의 합격/중단 기준.
(I01, I02, I04, I05, F04)

### Q04. E3와 VLM은 각각 어디까지만 맡기는 것이 좋을까요?

현재 E3는 이미지 전체 결함 후보 점수만 주며 유형·위치를 확인하지 못한다. VLM도 기본 연결만
확인했을 뿐 실제 결함 판정은 미자격이다. 사진 품질 검사·부위 설명·OCR·추가 사진 안내 중
VLM을 먼저 맡길 보조 기능은 무엇일까? 위치 검출/분할 모델이 꼭 필요한 요구는 무엇일까?
고객의 결함 주장에 VLM이 끌려가는 편향은 같은 사진의 문장 제공 전후 비교로 어떻게 측정할까?

받고 싶은 결과: 모델별 허용/금지 주장, 촬영 품질·보류 기준, 첫 비교 실험 1개.
(C01, C02, C04, D01, D03)

### Q05. RAG의 다음 개선은 질의 생성보다 정책 구조와 예외 검색이 먼저일까요?

Hybrid 검색은 있고 LLM Query Builder는 RAW보다 낮았다. 새 평가기는 본문만 찾고 예외를 놓친
경우를 구분할 수 있다. 원문 조건 손실·추출 오류·예외 누락·질의 분산 중 원인을 어떻게 나눌까?
정책의 표·각주·예외 연결, 검색 단위 변경, Top K 확대, reranker 중 무엇부터 비교해야 할까?

받고 싶은 결과: 같은 문의/정답에서 RAW와 후보를 비교하는 실험표, 실패 분류와 채택 기준.
검색 부족 시 무조건 문맥을 늘릴지, 추가 확인으로 보낼지도 결정한다. (F01, F02, F04, F05)

### Q06. 정책 검색·근거 설명·실행 규칙 사이의 의미 차이를 어떻게 검증할까요?

인용 ID의 유효성과 실제 문장이 조항으로 뒷받침되는 것은 다르다. 고객 정책을 조항과 정형
규칙으로 옮길 때 예외·특약·시행일·필수 증거의 의미가 바뀌지 않았는지 누가 어떻게 검수할까?
정책 변경 시 과거 Case의 근거는 보존하면서 새 버전을 적용·되돌리는 절차는 어떻게 구성할까?

받고 싶은 결과: 정책 원문↔조항↔규칙 검수표, 적용 시점/예외 우선순위와 변경 승인 책임.
(G01, G02, G03, G05)

### Q07. 두 모델의 대조 결과를 상담원이 오해하지 않게 어떻게 보여줄까요?

오프라인 대조는 ‘같은 유형의 후보’와 ‘미확인 이유’를 구분하지만 사실 확인·위치 일치·모순
판정은 하지 않는다. 합산 점수 하나보다 주장별 후보/보류/추가 자료를 제시하는 방식이 적절할까?
text-only·vision-only·결합의 근거 없는 지지/반박, 보류율, 상담원 수정량을 어떻게 비교할까?

받고 싶은 결과: 대조 결과의 화면 구획과 금지 표현, 효과 평가, 운영 저장·권한·보존 연결 조건.
(H01, H03, H04, H05, K03)

### Q08. GX10과 4090의 모델·프롬프트 비교에서 무엇을 고정해야 할까요?

Q5와 NVFP4의 개별 결과를 합쳐 최종 자격으로 사용할 수 없다. 모델 revision·양자화·런타임·
프롬프트·schema·문맥 길이·디코딩 조건을 어디까지 고정해야 재현 가능한 비교가 될까?
한 모델의 세 과제 구성과 과제별 구성을 어떤 품질/운영 기준으로 비교하고, 어떤 반복 오류에서
프롬프트나 검색 개선을 넘어 추가학습을 검토해야 할까?

받고 싶은 결과: GX10 전용 평가 식별 계약, 동일 조건 비교표, 과제별 실패/채택 기준.
(E01–E05, N03)

### Q09. 실제 고객 접수·첨부·분석·검토를 연결할 때 가장 먼저 보강할 경계는 무엇일까요?

상담원 콘솔과 비동기 처리 기반은 있지만 서명형 외부 접수는 Case 생성까지만 맡는다.
실제 사진 전송·배정·분석 시작·추가 자료 도착을 어느 시스템이 소유해야 할까? GPU 장애·broker
재전달·늦은 응답·부분 성공에서 중복/유실 방지, 사람의 재실행·취소 권한을 어떻게 검증할까?

받고 싶은 결과: 첫 고객 연동 범위·원본 시스템 책임표, 장애 시험표와 부분 실패 업무 흐름.
실제 환불/메일/CRM 쓰기는 별도 권한·승인·복구 계약 없이는 열지 않는다. (J02–J04, K01, K02, K04)

### Q10. 최근 보안 개선 이후에도 고객 도입 전에 반드시 확인할 것은 무엇일까요?

이미지 정화와 ClamAV 응답 처리는 오프라인으로 보강했으나 실제 HTTP 자격은 재검증해야 한다.
고객 IdP의 퇴사/권한 회수, worker·검색·파일·내보내기의 고객사 격리, 사진/OCR/정책의 악성
지시를 어떤 부정 시험으로 검증할까? 원문·파생본·해시·로그·백업의 보존/삭제 책임은 어떻게 나눌까?

받고 싶은 결과: 필수 위협/시험 목록과 고객 보안·개인정보 담당자의 확인 항목.
법률·계약 적합성은 기술 멘토의 일반 조언만으로 확정하지 않는다. (L01–L04, M01, M03, M05)

### Q11. 문의량에 맞는 서빙 구성과 운영 시험을 어떻게 정할까요?

실제 하루 문의량·사진/토큰 수·피크·상담원 수의 측정이 필요하다. 온프레미스·관리 전용 서버·
공유 SaaS 중 첫 고객에 맞는 형태와 연구/서비스 자원 분리를 어떻게 정할까? 큐 대기 포함
완료시간·실패율·장시간 안정성·원가를 어떤 시나리오로 시험하고, GPU 장애 시 수동 업무를
어떻게 유지할까? 경보의 실제 수신과 별도 호스트 반복 복원은 어떤 증거로 인정할까?

받고 싶은 결과: 첫 배포 형태, 처리량/지연 목표, 장애 담당·수동 경로·복원 시험과 비용 산식.
현재 복구 목표나 단일 canary 시간을 달성 실적으로 간주하지 않는다. (N01, N02, N04, N05, O02–O04)

### Q12. 출시 전 남은 일을 어떤 순서와 중단 기준으로 묶으면 좋을까요?

데이터 확보, RAG 오류 분석, Vision/VLM 역할 검증, 대조 UI 통합, 고객 운영 자격이 남아 있다.
다음 두 주에 가장 큰 불확실성을 줄일 세 가지는 무엇일까? 어떤 증거가 있어야 Shadow와
제한 권고 파일럿을 시작하고, 어떤 위험 오류·보류 급증·권한/복구 문제에서 중단할까?
배포·migration·모델/정책 버전·롤백을 누가 승인하며 재개 조건은 무엇일까?

받고 싶은 결과: 다음 과제 3개와 담당/선행 조건/완료 기준, 파일럿 시작·중단·재개 체크리스트.
(J05, O01, P01, P03–P05)

## 6. 회의 진행안과 준비물

멘토님의 전문 분야·회의 시간은 미확정이다. 아래는 60분 기준 제안이며 모든 질문을 다루기보다
데이터/평가 기준을 먼저 맞춘 뒤 전문 분야의 핵심 질문 2~3개를 선택한다.

| 시간 | 내용 | 기대 결과 |
|---|---|---|
| 0~10분 | 서비스·구현/미검증·이번 개선 설명 | 같은 현황 이해 |
| 10~25분 | Q01~Q03 범위·데이터·품질 기준 | 검증 가능한 첫 실험의 조건 |
| 25~45분 | AI/RAG: Q04~Q08 중 선택, 플랫폼: Q09~Q11 중 선택 | 비교할 옵션·실험과 금지 해석 |
| 45~55분 | Q10~Q12 고객 진입·운영·우선순위 | 놓치면 안 되는 승인/검증 조건 |
| 55~60분 | 다음 과제 3개 기록 | 담당자·선행 조건·결과물 |

회의 전 추가로 준비해야 하는 자료:

- [x] 개선 반영 후 현황과 핵심 질문 — 이 문서.
- [ ] 공유 권리가 확인된 성공·실패·판단불가 Case. 문의/사진/정책/사람 정답을 함께 준비.
- [ ] 같은 Case의 RAW/후보 검색 결과와 빠진 예외, Vision 관찰과 고객 주장 불일치 사례.
- [ ] 상담원 화면의 한 Case 경로. 실제 연결과 mock/합성 화면을 명확히 구분.
- [ ] 첫 고객의 하루 문의량·피크·사진 수·상담원 수와 데이터/연동 제공 가능 범위.

위 체크되지 않은 자료는 이미 준비됐다는 뜻이 아니다. 승인된 실제 자료가 없으면 합성 사례임을
표시한다. 고객 원문·사진·비밀번호·개인 키·접속 주소를 이 문서나 채팅에 넣지 않는다.
