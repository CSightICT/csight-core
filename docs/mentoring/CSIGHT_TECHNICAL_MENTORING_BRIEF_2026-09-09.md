# CSight 기술 멘토링 종합 자료

작성일: 2026-09-09 · 대상: 기술 멘토, 개발팀, 첫 고객사의 기술·운영 담당자

목적: 현재 구현과 검증 한계를 공유하고, 출시까지 필요한 기술 의사결정과 다음 실험을 구체화한다.
멘토의 답변이나 승인 결과를 미리 작성한 문서가 아니다.

## 읽는 방법

- 회의 전에는 1~4절을 먼저 읽는다. 서비스 설명, 현재 상태, 검증 수치, 우선 질문을 담았다.
- 5절은 16개 영역·80개 질문의 전체 목록이다. 한 회의에서 모두 답할 필요는 없다.
- 6~8절은 진행안, 준비 자료, 회의 후 결정·실행 기록 양식이다.
- 9절은 저장소 근거 문서다. 고객 원문·사진, 접속 주소, 비밀번호, 개인 키는 이 자료에 포함하지 않았다.
- 11절은 문서 작성 뒤 실제로 반영한 즉시 개선 항목이다. 질문 전체의 해결이나 모델 품질 통과와 구분한다.

상태 기준은 **2026-09-09 저장소 코드·문서와 기존 검증 기록**이다. 이번 문서 작성에서는 서버에
접속하거나 새 모델 평가를 하지 않았다. 마지막 GX10 실측은 **2026-09-02 20:01 KST**이며,
당시의 정상 응답을 오늘의 가동 상태나 서비스 품질 보증으로 해석하면 안 된다.
초기 Sprint 설계에 남아 있는 ‘미구현’ 문구는 최신 상태 원장과 후속 Accepted ADR로 보정했다.

## 1. 멘토에게 먼저 설명할 서비스

### 1.1 한 문장 소개

CSight는 고객 문의의 텍스트와 상품 사진을 분석하고 기업 정책의 근거를 찾아,
상담원이 불량·교환·환불 관련 문의를 검토하고 처리 근거를 남기도록 돕는 B2B CS 의사결정 지원 서비스다.

일반 FAQ 챗봇이나 완전 자동 환불 시스템이 아니다. 주요 AI 축은 Vision과 LLM이며,
실제 제품은 여기에 정책 검색, 결정적 규칙, 사람 검토, 기록·보안·운영 계층이 결합된 구조다.
VLM은 이미지도 입력받는 언어 모델의 활용 후보로, 기존 Vision의 결함 검증 능력을 자동으로 대체하지 않는다.

### 1.2 의도한 업무 흐름과 책임

| 단계 | 담당 역할 | 현재 경계 |
|---|---|---|
| 문의·이미지·상품/주문 접수 | Core와 상담원/연동 시스템 | Case와 Evidence 보존. 서명형 외부 접수는 Case 생성까지만 구현 |
| 문의 구조화 | LLM | 고객의 주장·요청·누락 정보를 추출. 고객의 진술을 사실 확정으로 바꾸지 않음 |
| 이미지 분석 | Vision, 필요 시 별도 검증된 VLM 보조 | 이미지에서 관찰한 것만 제공. 현재 E3는 이미지 전체 결함 점수만 반환 |
| 주장과 이미지 대조 | 진단용 대조 로직 | 9/9 오프라인 구현. 운영 DB·API·상담원 UI·정책에는 아직 연결하지 않음 |
| 정책 찾기와 설명 | RAG와 LLM | 관련 정책 후보·예외·출처를 제시. 검색 결과나 생성 문장이 적용 가능성을 확정하거나 최종 승인 권한을 갖지 않음 |
| 규칙 적용과 검토 요청 | 버전 고정 정책 엔진 | 정형 조건을 계산하고 검토 경로를 제안. 미확인 조건을 임의로 채우지 않음 |
| 최종 결정과 기록 | 인증된 담당자 | 사람 결정·근거·보고서 보존. 환불·메일 등 실제 외부 실행은 연결하지 않은 DRY_RUN |

### 1.3 우리가 중요하게 보는 것

1. **의미와 근거의 품질**: 잘못된 결함 설명, 빠진 예외 정책, 근거 없는 확신을 줄이는 것이 최우선이다.
2. **불확실성과 안전**: 모르면 보류하고 추가 증거를 요청한다. 최종 결정은 사람이 한다.
3. **실제 업무 처리 가능성**: 하루 문의량과 상담원 처리 한계에 맞추고, 실패·대기가 쌓이지 않게 한다.
4. **응답 속도**: 최저 지연 경쟁이 목적은 아니다. 문서당 약 5분에 이르는 지연은 피하고자 하며,
   큐 대기를 포함한 정식 목표와 측정 구간은 고객과 확정해야 한다.

어떤 과제의 필수 품질·안전 기준 실패도 다른 과제의 높은 점수나 빠른 속도로 상쇄하지 않는다.

### 1.4 이번 멘토링에서 받고 싶은 도움

‘더 큰 모델을 쓰자’는 일반론보다, **현재 어느 오류를 먼저 줄이고, 어떤 데이터로 비교하며,
어떤 증거가 있어야 고객에게 제공할 수 있는지**를 결정하고 싶다.
첫 적용 범위는 고객 1곳·상품군 1개·시각적 결함 2~3개가 기존 계획이지만, 실제 대상은 미확정이다. [S01, S02, S03]

## 4. 시간이 짧을 때 우선할 질문 12개

우선순위는 장애 등급이 아니라 의사결정 시점이다. P0는 제한 고객 파일럿 전에 답이 필요하고,
P1은 파일럿 설계·운영 및 개선에 필요하며, P2는 특정 오류나 확장 수요가 확인될 때 검토한다.
이 목록의 순서는 학습 가치와 의존성 기준이며, 보안·개인정보의 필수 조건을 뒤로 미룬다는 뜻이 아니다.

| 순서 | 질문 ID | 회의에서 바로 물을 질문 | 받아야 할 결과물 |
|---|---|---|---|
| 1 | A01 | 첫 상품군·결함 유형을 무엇으로 좁혀야 실제 검증과 도입 가능성이 가장 높은가? | 첫 PoC 지원/제외 범위 |
| 2 | B01, B02 | 어떤 Case Bundle과 독립 정답을 확보해야 두 엔진을 정직하게 평가할 수 있는가? | 데이터 계약·라벨링 기준·검수 책임 |
| 3 | I02 | 어떤 위험 오류는 절대 통과시키면 안 되며, 허용 오차는 어떤 표본으로 정할 것인가? | 위험별 품질 Gate와 표본 설계 |
| 4 | C01, D01 | E3, 위치 검출 모델, VLM을 각각 어디까지만 맡길 것인가? | 역할 분담 및 비교할 최소 후보 |

### H. 두 엔진 대조·불확실성·보류 — 5문항

신선한 증거, 깨끗한 배포 artifact, 모델 자격을 함께 충족해야 한다. 대규모 인프라·학습·자동 환불은

- 새 GPU 추론·학습·서비스 확인·Backend/UI 테스트는 실행하지 않았다. 문서 링크와 질문 ID/구성만 검사했다.
- 상세 문서 검사 결과: [작성 검증 JSON](CSIGHT_TECHNICAL_MENTORING_VERIFICATION_2026-09-09.json).

다음 세션에서는 이 문서에서 고른 질문 ID와 실제 멘토 답변을 기록하고,
**첫 적용 범위, 데이터/정답, 품질 Gate, 다음 비교 실험, 고객 운영 책임**을 우선 확정한다.
