01 / SYSTEM

분석은 모델이, 결정은 사람이.

구현된 업무 흐름입니다. 최종 모델의 고객 품질·운영 자격은 아직 확보하지 않았습니다.

RAG·정책 엔진·사람 검토는 이미 구현했습니다. 실제 환불·메일·CRM 쓰기는 연결하지 않고 모의 처리로 제한합니다. 고객 파일럿의 시작 조건은 아직 충족하지 못했습니다.

LLM · RAG세 과제와 Hybrid 검색 구현 · 최종 공동 품질은 미확보

구현: 문의 구조화, Query Builder, 근거 설명. 정책 조항·버전, BM25+dense+RRF, 고객사·유효기간 선필터와 고정 인용 묶음.

남은 검증: 최종 동일 모델·프롬프트·런타임의 세 과제 공동 품질. Query Builder는 RAW→HYBRID 기준 미달이므로 기본 RAW 경로를 유지합니다. 실제 정책의 표·각주·예외 연결과 갱신 운영도 필요합니다.

Vision · VLM · 대조E3는 이미지 전체 점수 · 유형·위치 확인과 실제 결합 효과는 미검증

현재 경계: E3의 ANY_DEFECT 점수는 결함 종류·위치·bbox를 제공하지 않습니다. 낮은 점수도 정상 확정이 아닙니다. VLM의 고객 사진·미세 결함·OCR 품질은 미자격입니다.

대조 모듈: 유형 후보·미확인 이유·추가 자료를 제시하는 오프라인 진단입니다. 사실 확인·위치 일치·모순 판정을 하지 않으며, 실제 효과와 운영 저장·권한·보존·UI 연결은 남아 있습니다.

서비스 · 데이터상담원 콘솔·비동기·불변 이력 구현 · 실제 고객 연동은 남음

기반: Python/FastAPI 모듈형 모놀리스와 ports/adapters, PostgreSQL/pgvector, private MinIO, RabbitMQ/Celery. Outbox·멱등성·재시도와 불변 실행 이력을 갖췄습니다.

제품: React/TypeScript 콘솔의 접수·배정·검토·추가 자료·사람 결정·보고서. 실제 상담원 사용성·CRM·사진 첨부 연동, 부하·부분 장애·복구 및 운영 재실행/취소 자격은 검증해야 합니다.

보안 · 운영인증·격리·파일 검사 기반 구현 · 고객 환경에서 다시 검증 필요

구현: OIDC/PKCE, 역할/소유권, DB RLS, 파일 정화·검사, 원문/파생본 삭제와 기록 분리. 데모와 분리한 파일럿 구성·진입 점검 및 관측·복원 절차.

도입 조건: 고객 IdP·권한 회수·자료 사용권·보존/백업·키 운영, 경보 실제 수신과 별도 호스트 반복 복원. 고객 환경의 접수부터 저장·접근·삭제까지 전체 보안 경로를 검증해야 합니다.

지원 범위 · 데이터 · 평가
Q01

첫 출시의 지원 범위를 어디까지 좁히는 것이 적절할까요?

현재 고객 1곳·상품군 1개·시각적 결함 2~3개로 시작하는 안이 있으나 대상은 미확정입니다. 시각적으로 확인 가능한 불량, 문의 빈도, 정상 참고 사진 확보 가능성, 오류 비용 중 무엇을 우선해 골라야 할까요? 사진으로 판단할 수 없는 작동·냄새·책임 문제는 어떤 수동 경로로 제외할까요?

논의를 통해 정할 사항첫 지원/제외 범위와 상담원에게 제공할 최소 기능 1장.

Q02

두 엔진을 제대로 평가하려면 어떤 데이터와 독립 정답부터 모아야 할까요?

합성 평가와 선별 시연 자료는 있지만 실제 문의·전체 사진·주문 맥락·당시 정책이 연결된 대표 자료가 부족합니다. 고객 주장, 사진에서 관찰 가능한 사실, 정책상 처리의 정답을 어떻게 분리하고 검수할까요? 동일 상품·주문·촬영·유사 이미지 누출을 막는 분할과 표본 구성은 어떻게 정할까요?

논의를 통해 정할 사항최소 Case Bundle, 라벨/이견 조정 기준, 검수자, 그룹 분할·사용권 확인표. 초기 소량 수집과 통계적 품질 보증에 필요한 표본은 분리하고자 합니다.

Q03

무엇을 측정하고 어느 수준이어야 제한 파일럿을 허용할까요?

실제 고객 업무의 품질과 허용 오류 기준은 아직 확정하지 않았습니다. 잘못된 정책 적용·근거 없는 확신·개인정보 노출처럼 중대 위험은 어떤 절대 기준으로 막고, 추출·검색·설명·Vision·대조·업무 효과는 어떤 분리 지표와 신뢰구간으로 평가할까요? AI 채점 보조와 사람 검수의 역할은 어떻게 구분할까요?

논의를 통해 정할 사항위험별 평가 카드, 사람 검수 범위, 표본 계획과 파일럿 합격/중단 기준.

AI 엔진과 정책 근거

Q04

E3와 VLM은 각각 어디까지만 맡기는 것이 좋을까요?

현재 E3는 이미지 전체 결함 후보 점수만 주며 유형·위치를 확인하지 못합니다. VLM도 기본 연결만 확인했을 뿐 실제 결함 판정은 아직 검증되지 않았습니다. 사진 품질 검사·부위 설명·OCR·추가 사진 안내 중 VLM을 먼저 맡길 보조 기능은 무엇일까요? 위치 검출/분할 모델이 꼭 필요한 요구는 무엇일까요? 고객의 결함 주장에 VLM이 끌려가는 편향은 같은 사진의 문장 제공 전후 비교로 어떻게 측정할까요?

논의를 통해 정할 사항모델별 허용/금지 주장, 촬영 품질·보류 기준, 첫 비교 실험 1개.

Q05

RAG의 다음 개선은 질의 생성보다 정책 구조와 예외 검색이 먼저일까요?

Hybrid 검색은 구현했으나 LLM Query Builder는 RAW의 성능에 미치지 못했습니다. 원문 조건 손실·추출 오류·예외 누락·질의 분산 중 원인을 어떻게 나눌까요? 정책의 표·각주·예외 연결, 검색 단위 변경, Top K 확대, reranker 중 무엇부터 비교해야 할까요?

논의를 통해 정할 사항같은 문의/정답에서 RAW와 후보를 비교하는 실험표, 실패 분류와 채택 기준. 검색이 불충분하면 문맥을 늘릴지, 추가 확인으로 보낼지도 정리하고자 합니다.

Q06

정책 검색·근거 설명·실행 규칙 사이의 의미 차이를 어떻게 검증할까요?

인용 ID가 유효한 것과 실제 문장이 조항으로 뒷받침되는 것은 다릅니다. 고객 정책을 조항과 정형 규칙으로 옮길 때 예외·특약·시행일·필수 증거의 의미가 바뀌지 않았는지 누가 어떻게 검수할까요? 정책 변경 시 과거 Case의 근거는 보존하면서 새 버전을 적용·되돌리는 절차는 어떻게 구성할까요?

논의를 통해 정할 사항정책 원문↔조항↔규칙 검수표, 적용 시점/예외 우선순위와 변경 승인 책임.

Q07

두 모델의 대조 결과를 상담원이 오해하지 않게 어떻게 보여줄까요?

오프라인 대조는 ‘같은 유형의 후보’와 ‘미확인 이유’를 구분하지만 사실 확인·위치 일치·모순 판정은 하지 않습니다. 합산 점수 하나보다 주장별 후보/보류/추가 자료를 제시하는 방식이 적절할까요? text-only·vision-only·결합의 근거 없는 지지/반박, 보류율, 상담원 수정량을 어떻게 비교할까요?

논의를 통해 정할 사항대조 결과의 화면 구획과 금지 표현, 효과 평가, 운영 저장·권한·보존 연결 조건.

Q08

GX10과 4090의 모델·프롬프트 비교에서 무엇을 고정해야 할까요?

Q5와 NVFP4의 개별 결과를 합쳐 최종 자격으로 사용할 수 없습니다. 모델 revision·양자화·런타임· 프롬프트·schema·문맥 길이·디코딩 조건을 어디까지 고정해야 재현 가능한 비교가 될까요? 한 모델의 세 과제 구성과 과제별 구성을 어떤 품질/운영 기준으로 비교하고, 어떤 반복 오류에서 프롬프트나 검색 개선을 넘어 추가학습을 검토해야 할까요?

논의를 통해 정할 사항GX10 전용 평가 식별 계약, 동일 조건 비교표, 과제별 실패/채택 기준.

고객 도입과 운영

연동 · 보안 · 인프라 · 출시 조건
Q09

실제 고객 접수·첨부·분석·검토를 연결할 때 가장 먼저 보강할 경계는 무엇일까요?

상담원 콘솔과 비동기 처리 기반은 있지만 서명형 외부 접수는 Case 생성까지만 맡습니다. 실제 사진 전송·배정·분석 시작·추가 자료 도착을 어느 시스템이 소유해야 할까요? GPU 장애·broker 재전달·늦은 응답·부분 성공에서 중복/유실 방지, 사람의 재실행·취소 권한을 어떻게 검증할까요?

논의를 통해 정할 사항첫 고객 연동 범위·원본 시스템 책임표, 장애 시험표와 부분 실패 업무 흐름. 실제 환불/메일/CRM 쓰기는 별도 권한·승인·복구 계약 없이는 허용하지 않습니다.

Q10

고객 도입 전에 어떤 보안·개인정보 검증이 필요할까요?

고객 환경의 접수·저장·접근·삭제 전 과정에 대한 보안 검증이 필요합니다. 고객 IdP의 퇴사/권한 회수, worker·검색·파일·내보내기의 고객사 격리, 사진/OCR/정책의 악성 지시를 어떤 부정 시험으로 검증할까요? 원문·파생본·해시·로그·백업의 보존/삭제 책임은 어떻게 나눌까요?

논의를 통해 정할 사항필수 위협/시험 목록과 고객 보안·개인정보 담당자의 확인 항목. 법률·계약 적합성은 기술 멘토의 일반 조언만으로 확정하지 않습니다.

Q11

문의량에 맞는 서빙 구성과 운영 시험을 어떻게 정할까요?

실제 하루 문의량·사진/토큰 수·피크·상담원 수의 측정이 필요합니다. 온프레미스·관리 전용 서버·공유 SaaS 중 첫 고객에 맞는 형태와 연구/서비스 자원 분리를 어떻게 정할까요? 큐 대기 포함 완료시간·실패율·장시간 안정성·원가를 어떤 시나리오로 시험하고, GPU 장애 시 수동 업무를 어떻게 유지할까요? 경보의 실제 수신과 별도 호스트 반복 복원은 어떤 증거로 인정할까요?

논의를 통해 정할 사항첫 배포 형태, 처리량/지연 목표, 장애 담당·수동 경로·복원 시험과 비용 산식. 현재 복구 목표나 단일 canary 시간을 달성 실적으로 간주하지 않습니다.

Q12
